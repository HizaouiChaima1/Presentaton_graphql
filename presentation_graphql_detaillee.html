02 · Contexte

Comment une application échange-t-elle avec un serveur ?

Une application frontend (site web ou application mobile) a souvent besoin de données stockées sur un serveur : profils, produits, commandes, messages, etc.

Frontend
⇄
API
Point de communication
⇄

L’API reçoit les demandes du client, interroge les sources de données et renvoie une réponse. REST est une approche très utilisée pour construire ces API. GraphQL propose une autre façon de formuler les demandes.

03 · Le problème

Les limites fréquemment rencontrées avec REST

Over-fetching

Trop de données

Le client demande les informations d’un utilisateur, mais l’endpoint renvoie aussi son adresse, sa date de naissance et d’autres champs inutiles à l’écran.

Conséquence : transfert de données superflu.

Under-fetching

Pas assez de données

Pour afficher un profil avec ses publications, le client doit appeler un endpoint pour le profil, puis un autre pour les publications.

Conséquence : plusieurs appels et une logique frontend plus complexe.

Ces situations ne signifient pas que REST est mauvais. Elles montrent simplement que certains écrans ont besoin d’une récupération de données plus flexible.

04 · Définition

Qu’est-ce que GraphQL ?

GraphQL est un langage de requête pour les API et un environnement d’exécution côté serveur. Il permet au client de décrire précisément les données qu’il souhaite obtenir.

Langage de requête

Le client écrit une requête structurée pour exprimer son besoin.

Schéma typé

Le serveur décrit les types, champs et opérations disponibles.

Exécution serveur

Le serveur exécute la requête et construit une réponse conforme à sa structure.

GraphQL a été développé chez Facebook à partir de 2012 et rendu open source en 2015. Il peut être utilisé avec différentes bases de données et différents langages de programmation.

05 · Exemple simple

Le client choisit les champs souhaités

Imaginons une application qui affiche une petite fiche utilisateur. Elle a uniquement besoin du nom et de l’adresse e-mail.

Requête GraphQL

query {
  user(id: 7) {
    name
    email
  }
}

Le client demande les champs name et email.

Réponse JSON

{
  "data": {
    "user": {
      "name": "Ahmed",
      "email": "ahmed@example.com"
    }
  }
}

La réponse reprend la structure demandée.

Important GraphQL ne choisit pas automatiquement les données : le client les sélectionne parmi les champs autorisés par le schéma du serveur.

07 · Schéma

Le Schema : le contrat de l’API

Le schéma définit ce que le client a le droit de demander. Il décrit les objets, leurs champs et les opérations disponibles. Il sert de contrat entre le frontend et le backend.

type User {
  id: ID!
  name: String!
  email: String!
}

type Query {
  user(id: ID!): User
}
  • type User : décrit un objet utilisateur.
  • String : représente une chaîne de caractères.
  • ID : représente un identifiant.
  • ! : indique que la valeur ne peut pas être nulle.
  • type Query : définit les opérations de lecture disponibles.
08 · Resolvers

Le rôle des resolvers

Le schéma annonce les champs disponibles, mais il ne contient pas à lui seul la logique pour récupérer les informations. Les resolvers réalisent ce travail.

const resolvers = {
  Query: {
    user: async (_, args, context) => {
      return context.db.users.findById(args.id);
    }
  }
};

Le schéma

Déclare qu’une requête user existe et retourne un utilisateur.

Le resolver

Explique comment trouver cet utilisateur, par exemple en interrogeant la base de données.

Exemple illustratif en JavaScript : l’implémentation exacte dépend du serveur et de la bibliothèque utilisés.

09 · Cycle d’exécution

Que se passe-t-il lorsqu’une requête arrive ?

  1. Envoi : le client envoie une requête au serveur GraphQL.
  2. Analyse : le serveur vérifie que la requête est correctement écrite.
  3. Validation : les champs demandés doivent exister dans le schéma et respecter les types.
  4. Exécution : les resolvers sont appelés pour obtenir les valeurs.
  5. Réponse : le serveur renvoie généralement un objet JSON contenant les données et éventuellement des erreurs.

10 · Query

Query : lire des informations

Une Query permet de récupérer des données sans demander au serveur de les modifier. Elle ressemble à une opération de lecture.

query {
  user(id: 7) {
    name
    email
  }
}

On peut aussi demander plusieurs informations liées, si le schéma les autorise :

query {
  user(id: 7) {
    name
    posts {
      title
    }
  }
}

Cette requête demande le nom de l’utilisateur et les titres de ses publications. Les champs disponibles dépendent toujours du schéma.

11 · Mutation

Mutation : modifier les données

Une Mutation sert à effectuer une action qui modifie l’état des données : création, mise à jour ou suppression.

mutation {
  createUser(name: "Raja", email: "raja@example.com") {
    id
    name
    email
  }
}

Création

Ajouter un nouvel utilisateur ou un nouveau produit.

Mise à jour

Modifier le nom, l’adresse ou le statut d’un élément.

Suppression

Supprimer une ressource selon les droits de l’utilisateur.

Retour

La mutation peut renvoyer les champs utiles après l’opération.

12 · Subscription

Subscription : recevoir les mises à jour en temps réel

Une Subscription permet à un client de rester abonné à un événement. Lorsque cet événement se produit, le serveur peut transmettre une nouvelle information au client.

subscription {
  messageAdded {
    id
    content
    author
  }
}

Exemple concret : dans une application de discussion, lorsqu’un utilisateur envoie un message, les autres participants peuvent le recevoir sans actualiser la page.

Les subscriptions sont généralement mises en œuvre avec une connexion persistante, par exemple WebSocket, selon la configuration du serveur.

14 · Avantages

Pourquoi choisir GraphQL ?

Requêtes précises

Le client demande uniquement les champs dont son interface a besoin.

Moins d’allers-retours

Des données liées peuvent être obtenues dans une seule opération.

Schéma documenté

Le schéma décrit les capacités de l’API et facilite la découverte des champs.

Évolution contrôlée

De nouveaux champs peuvent être ajoutés sans nécessairement créer une nouvelle version d’endpoint.

15 · Limites

Les inconvénients et difficultés

  • Complexité initiale : il faut concevoir le schéma, les resolvers et les règles d’accès.
  • Cache : les réponses GraphQL utilisent souvent POST et nécessitent une stratégie de cache adaptée.
  • Requêtes coûteuses : une requête imbriquée peut demander beaucoup de ressources au serveur.
  • Problème N+1 : certains resolvers peuvent déclencher trop de requêtes vers la base de données. Des outils comme DataLoader aident à regrouper ces accès.
  • Sécurité : il faut contrôler les autorisations, la profondeur et le coût des requêtes.

GraphQL apporte de la flexibilité, mais cette flexibilité doit être encadrée par une bonne conception.

16 · Sécurité et bonnes pratiques

Comment sécuriser une API GraphQL ?

Authentification

Identifier l’utilisateur, par exemple avec une session ou un jeton.

Autorisation

Vérifier qu’il a le droit d’accéder à chaque ressource ou action.

Limitation des requêtes

Contrôler la profondeur, le coût et la taille des requêtes.

Validation des entrées

Vérifier les paramètres et éviter d’exposer des informations sensibles.

Il ne faut jamais considérer qu’un champ est accessible simplement parce qu’il existe dans le schéma : les permissions doivent être vérifiées côté serveur.

17 · Écosystème

Outils et technologies compatibles

GraphQL n’impose pas un langage de programmation ni une base de données spécifique.

Serveur

Apollo Server, GraphQL Yoga, Spring for GraphQL.

Client

Apollo Client, Relay, urql.

Langages

JavaScript, TypeScript, Java, Python, PHP et autres.

Bases SQL

PostgreSQL, MySQL, SQL Server.

Bases NoSQL

MongoDB et autres systèmes compatibles.

Exploration

GraphiQL et Apollo Sandbox pour tester les requêtes.

18 · Cas d’utilisation

Quand utiliser GraphQL ?

Application mobile

Limiter les données transférées sur une connexion parfois lente.

Tableau de bord

Assembler des informations provenant de plusieurs ressources.

Application sociale

Afficher des profils, publications, commentaires et réactions.

Écosystème de services

Fournir une interface de données unifiée au frontend.

Pour une API simple avec des ressources CRUD classiques, REST peut rester plus facile à mettre en place et à maintenir.

19 · Conclusion

Ce qu’il faut retenir

GraphQL est une technologie conçue pour rendre les échanges entre le client et le serveur plus flexibles.

Query

Lire les données.

Mutation

Modifier les données.

Subscription

Recevoir des événements.

Son schéma typé, ses resolvers et ses requêtes personnalisées sont ses éléments fondamentaux. Il ne remplace pas REST dans tous les cas, mais constitue une alternative intéressante lorsque les besoins de récupération de données sont complexes.
